# Asset integration guide (Hunyuan models, animations, courtyard)

Everything visual in KENGEKI is a placeholder that sits behind a stable interface. Replacing
assets never requires changes to the combat, AI or encounter code.

## Placeholders to replace

| # | Placeholder | Where | Replace with |
|---|---|---|---|
| 1 | Samurai body (primitives) | `scenes/characters/samurai_visual_placeholder.tscn`, used by `player.tscn` → `Visual` | Hunyuan **samurai** model through `ImportedHumanoidVisual` |
| 2 | Ronin body (primitives with straw kasa) | `scenes/characters/ronin_visual_placeholder.tscn`, used by `enemy.tscn` → `Visual` | Hunyuan **ronin** model(s) through `ImportedHumanoidVisual` |
| 3 | Katana (boxes plus a disc) | `scenes/weapons/katana.tscn` | Hunyuan **katana** model |
| 4 | Pose-keyed procedural animation | `scripts/visual/placeholder_humanoid.gd` | Hunyuan **motion clips** (list below) |
| 5 | Courtyard blockout visuals | `scenes/arena/arena.tscn` → `Blockout` (Visual layer) | Hunyuan **castle courtyard** under `Arena/Visual` |
| 6 | Castle keep backdrop (boxes) | generated by `courtyard_blockout.gd` | part of the Hunyuan courtyard or world asset |
| 7 | Blade trail, sparks, impact droplets, dust | `scripts/vfx/blade_trail.gd`, `autoload/combat_fx.gd` | optional: textured trail and particle materials |
| 8 | Sky and lighting | `arena.tscn` → `Sun`, `WorldEnvironment` | keep or re-tune to match the courtyard |
| 9 | Music and all SFX | `audio/` | see [AUDIO.md](AUDIO.md) |
| 10 | UI style (flat panels) | `scripts/ui/ui_style.gd` | final UI artwork |

Put source assets in `assets/models/`, `assets/animations/` and `assets/environment/`.

## 1. Characters (samurai and ronin)

1. Import the `.glb` or `.fbx` into `assets/models/`. In the **Advanced Import Settings**:
   * Select the `Skeleton3D`, then *Retarget → Bone Map → New SkeletonProfileHumanoid*. Check that
     the bones auto-mapped (Hips, Spine, Chest, Neck, Head, LeftUpperArm…, **RightHand**, …).
   * Enable *Rest Fixer → Overwrite Axis*. This keeps every humanoid sharing the same rest pose,
     so one animation library drives both the samurai and the ronin.
   * The model should face **−Z**. If it faces +Z, leave `model_yaw_degrees = 180` (the default).
2. Make a visual scene, for example `scenes/characters/samurai_visual_hunyuan.tscn`. Its root is
   a `Node3D` named `Visual`, and its script is `res://scripts/visual/imported_humanoid_visual.gd`.
   Set:
   * `model_scene`: the imported model.
   * `weapon_bone`: `RightHand` after retargeting.
   * `weapon_offset`: the transform that puts the katana grip in the palm. The katana's origin is
     the grip, and the blade points along −Z.
   * `animation_map`: logical name → clip name in your library. The defaults are listed below.
3. In `player.tscn` (or `enemy.tscn`), delete the `Visual` child and instance your new scene with
   the same node name, **`Visual`**. Nothing else changes.

A player and an enemy can share the same model scene. Only the controller differs.

### Animation clips

These are the logical names that `ImportedHumanoidVisual.animation_map` expects:

| Logical name | Used for | Notes |
|---|---|---|
| `idle`, `walk`, `run` | locomotion | walk ≈ 4.6 m/s, run ≈ 7.4 m/s (player) / 4.6 m/s (enemy) |
| `strafe_left`, `strafe_right`, `walk_back` | lock-on movement | |
| `block`, `block_impact` | guard | `block` should loop |
| `dodge` | dodge | time-stretched to 0.42 s |
| `hit_light`, `hit_heavy`, `knockdown` | hit reactions | |
| `parried` | recoil after being parried | time-stretched to the stagger time |
| `death` | death | |
| `slash_rl`, `slash_lr` | light cuts I and II; enemy slash and return cut | |
| `overhead` | heavy cut, enemy overhead, Todome | |
| `rising` | Rising Cut | |
| `thrust` | Piercing Thrust, enemy thrust | |
| `kesa` | Kesa-giri finisher, Kaeshi-waza counter | |
| `spin` | Crescent Wheel finisher | |

Movement is driven by code, so export the clips **in place**, without root motion.
`footstep` method-track events (see below) trigger footstep sounds.

### Attack timing

Each attack's startup, active and recovery times live in `resources/attacks/**.tres`. There are
two ways to make an animation drive them:

* **Stretch** (default, `timing_source = DATA`): the clip is time-scaled so that its length
  matches `startup + active + recovery`. Author clips with the hit at about the same fraction of
  the clip, or tweak the timings in the `.tres` files to match the clip.
* **Animation events** (`timing_source = ANIMATION_EVENTS`): add a **Call Method** track to the
  clip, targeting the `Visual` node (from the AnimationPlayer's root model, the path is `..`).
  Key `emit_animation_event` with the argument `&"hit_start"` when the blade begins its cut,
  `&"hit_end"` when it stops, and `&"attack_end"` when the character can act again. If an event
  is missing, the data timing applies after twice its value, so an attack can never hang. This
  path is covered by the automated test `test_imported_visual_pipeline`.

For hit detection that follows the actual blade, set `WeaponComponent.detection_mode =
BLADE_AREA` in `player.tscn` or `enemy.tscn`. It uses the katana's `BladeArea` against each
fighter's hurtbox. The default `ARC_SWEEP` works with any animation and is more forgiving.

## 2. Katana

Open `scenes/weapons/katana.tscn` and set `build_placeholder = false`. Add the Hunyuan katana
mesh as a child with its grip at the origin and the blade along −Z, then move the **BladeBase**
and **BladeTip** markers onto the real blade. The trail, sparks and blade-area hit box all read
these markers.

## 3. Courtyard

1. Import the Hunyuan courtyard into `assets/environment/` and instance it under `Arena/Visual`.
2. Select `Arena/Blockout` and untick `show_visuals`. The invisible collision (ground, walls,
   lanterns, tree, racks) stays active.
3. Either keep the blockout collision and adjust its sizes in `courtyard_blockout.gd`
   (`half_size`, `wall_height`, obstacle positions), or turn off `build_collision` and give the
   Hunyuan scene its own `StaticBody3D` collision on **layer 1**. Put that collision in the
   group **`nav_source`** so the navmesh bakes from it. Prefer simple box or convex shapes;
   trimesh collision of a dense mesh is slow.
4. Move the `Arena/PlayerStart` and `Arena/SpawnPoints/*` markers to match the new layout (keep
   at least 6–8 spawn points near the entrances). If the walkable area is larger than 42 × 42 m,
   update `filter_baking_aabb` in `arena.gd` and `arena_half_extent` on the EncounterManager.
